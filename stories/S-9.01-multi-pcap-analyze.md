# S-9.01: Multi-PCAP / rotated-capture analyze

## Narrative

- **As an** OT analyst handed a directory of rotated captures
  (`capture-2024-10-01.pcap` … `capture-2024-10-07.pcap` produced by
  `tcpdump -G`, a SPAN appliance, or a size-rotating tap)
- **I want** `otsniff analyze a.pcap b.pcap c.pcap -o report.html` to ingest
  the files in command-line order and treat them as one logical capture
- **So that** I get a single report covering the union window without first
  running `mergecap` from Wireshark — one fewer tool, one fewer step, and no
  doubt about whether timestamps survived an external merge

## Acceptance Criteria

### AC-001 — CLI accepts one-or-more positional inputs (traces to BC-1.01.003 precondition)

`src/cli.rs`: `AnalyzeArgs.input: PathBuf` becomes
`AnalyzeArgs.inputs: Vec<PathBuf>` with:

```rust
#[arg(value_name = "PCAP", num_args = 1.., required = true)]
pub inputs: Vec<PathBuf>,
```

- `otsniff analyze a.pcap -o r.html` (exactly one file) produces **byte-identical**
  output to the pre-S-9.01 single-file path. No snapshot churn for the
  one-file case (see AC-005).
- `otsniff analyze` (zero positional inputs) fails with clap's usage error
  (exit code 2 — clap default for missing required args). otsniff does not
  reach the ingestion path.
- The `scrub` and `diff` subcommands are **out of scope**: they keep their
  single-file / two-file positional signatures. P0-10 is `analyze`-only.
- **Tests (`tests/cli_smoke.rs`):**
  - one-file analyze still succeeds and writes a report
  - `analyze` with no positional arg exits non-zero with a usage message
  - two-file analyze succeeds and writes one report

### AC-002 — Ordered concatenated ingestion (traces to BC-1.01.003 postcondition)

`src/pcap.rs` exposes a multi-file iterator that yields every packet of
`paths[0]` in file order, then every packet of `paths[1]`, etc.:

```rust
pub fn iter_packets_multi(paths: &[PathBuf]) -> Result<MultiPacketIter>;
```

- **Append / CLI-order semantics:** packets are concatenated in the order the
  files are named. The stream is **not** re-sorted by timestamp (this matches
  `mergecap -a`, not `mergecap`'s default timestamp merge). This is a
  deliberate, documented choice — the operator controls order via the CLI.
- `analyze()` in `src/cli.rs` is updated to take `&[PathBuf]` and drive the
  observer from the concatenated stream. The observer is unchanged
  (BC-1.01.001): `obs.first_ts` = first packet of the first file,
  `obs.last_ts` = last packet of the last file (existing `get_or_insert` /
  `last_ts = Some(pkt.ts)` semantics give the union window automatically when
  the files are in chronological order — the real rotated-capture case).
- **Fail-fast on per-file error:** if file N is missing, truncated, or
  unreadable, the error surfaces identifying that file (the existing
  `OtError::InputOpen { path, .. }` / `OtError::BadInput { path, .. }` carry
  the path). Files after the failure are not processed; no partial report is
  written.
- The progress reporter (S-5.01) keeps receiving one `record_packet` call per
  decoded packet across all files — no per-file reset.
- **Tests (`src/pcap.rs` inline):**
  - two single-packet synthetic legacy-pcap byte fixtures chained →
    `iter_packets_multi` yields exactly 2 packets, in file order
  - the first packet's `ts` precedes the second's; the concatenation
    preserves per-packet timestamps
  - a path list whose second entry does not exist → the iterator surfaces an
    `Err` naming the missing file (no panic, first file's packets still
    yielded before the error)

### AC-003 — Link-layer homogeneity guard (traces to BC-1.01.004)

Before streaming, each file's declared link-layer type is peeked and compared:

```rust
fn peek_link_type(path: &Path) -> Result<Option<Linktype>>;
```

- `iter_packets_multi` (or a pre-flight inside it) reads just enough of each
  file to determine its link type (legacy pcap: the 24-byte global header's
  `network` field; pcapng: the first Interface Description Block). If two files
  declare **different determinate** link types, it returns a new error variant
  `OtError::MixedLinkTypes` whose message names the offending files and their
  types, e.g.:
  `cannot merge captures with differing link-layer types: a.pcap=ETHERNET, b.pcap=LINUX_SLL`
- otsniff currently decodes **only** `ETHERNET` (`pcap.rs::decode_block`
  returns `OtError::UnsupportedLinkType` otherwise). The guard adds an
  explicit, *earlier*, clearer error for the mixed-set case rather than a
  mid-stream `UnsupportedLinkType` after file 0 was already processed.
- **pcapng caveat (documented):** a pcapng file whose link type cannot be
  determined before the first packet block (no IDB read) is treated as
  `ETHERNET`, matching the existing `decode_block` default
  (`link_type.unwrap_or(Linktype::ETHERNET)`). The guard compares only
  determinate types; indeterminate pcapng files are not rejected by the guard
  (they will still fail in `decode_ethernet` if genuinely non-Ethernet). This
  is recorded as tech-debt for a future "full IDB link-type read" story.
- `OtError::MixedLinkTypes` maps to `EX_DATAERR` (65), consistent with
  `UnsupportedLinkType` (the sibling link-type error) — it is a data/bad-input
  condition. (Note: `BadInput` itself maps to exit 2; an earlier draft of this
  AC conflated the two. The implementation correctly groups `MixedLinkTypes`
  with `UnsupportedLinkType` at 65 — see `error.rs::exit_code` and the
  `mixed_link_types_is_exit_65` test. Adversary m-2.)
- **Tests:**
  - two ETHERNET legacy-pcap fixtures pass the guard (no error)
  - an ETHERNET fixture + a synthesized non-ETHERNET legacy header
    (`network` = `LINKTYPE_LINUX_SLL` = 113) → `OtError::MixedLinkTypes`,
    message contains both file names and both type names
  - a single-file list never triggers the guard (nothing to compare)

### AC-004 — Per-file audit attribution (traces to BC-7.01.005 postcondition)

`src/audit.rs`: `AuditLog.input_pcap: InputDescriptor` becomes
`AuditLog.input_pcaps: Vec<InputDescriptor>`, one descriptor per input file
in CLI order. `SCHEMA_VERSION` is bumped `1 → 2` to signal the shape change.

- Each `InputDescriptor` keeps its existing fields (`path` = **basename only**
  per F-ADV-P2-009, `size_bytes`, `sha256`). Each file's SHA-256 still pins the
  exact bytes ingested from that file (BC-7.01.002 preserved per file).
- A single-file `--ai` run produces `input_pcaps` with exactly one element
  (the same descriptor the old singular field carried), plus
  `schema_version: 2`.
- The audit log is only written with `--ai`. Snapshot/JSON tests that assert
  the audit-log shape are updated via `cargo insta review` (the schema bump and
  the `input_pcap` → `input_pcaps` rename are the only audit diffs).
- **Tests (`src/audit.rs` inline + `tests/snapshot.rs`):**
  - `AuditLog` with two inputs serializes `input_pcaps` as a 2-element array;
    each element carries the correct basename + size + sha256
  - `schema_version` serializes as `2`
  - leak/no-real-identifier assertions (BC-7.01.003) still hold over the vec

### AC-005 — Report source label for multi-file (traces to BC-7.01.003 / F-ADV-P2-009)

- **Single-file:** the rendered HTML source string and the markdown
  `source_label` are **unchanged** from today (HTML: `args.input.display()`;
  MD: basename via `file_name()`). This guarantees zero snapshot churn for the
  existing single-file output.
- **Multi-file:** both surfaces use a **basename-only** combined label so no
  full path leaks (F-ADV-P2-009). Format: comma-joined basenames, e.g.
  `capture-01.pcap, capture-02.pcap, capture-03.pcap`. (Cap the joined string
  at a reasonable length — e.g. first 3 names then `… (+N more)` — to keep the
  report header readable for large rotated sets.)
- **Tests:**
  - a two-file analyze run's markdown shows both basenames, no `/` path
    separator from an absolute path
  - the single-file markdown/HTML snapshots remain green unmodified

### AC-006 — Documented edge cases & robustness

| ID | Scenario | Expected behavior |
|----|----------|-------------------|
| EC-001 | Exactly one input file | Identical behavior + output to pre-S-9.01 single-file analyze |
| EC-002 | Zero input files | clap usage error, non-zero exit; ingestion not reached |
| EC-003 | Files declare different link types | `OtError::MixedLinkTypes`, no report written |
| EC-004 | File N missing / truncated | Fail-fast `OtError` naming file N; no partial report |
| EC-005 | Out-of-order timestamps across files (file B older than file A) | Append/CLI-order honored; window = [first processed ts, last processed ts]; no sort — operator's responsibility (documented) |
| EC-006 | Same path passed twice | Processed twice (packets double-counted); otsniff does not dedupe the path list — operator controls it (documented) |
| EC-007 | One pcapng + one legacy pcap, both ETHERNET | Allowed — link type matches; concatenated normally |
| EC-008 | Large rotated set (e.g. 30 files) | All concatenated; source label truncates to first 3 + `… (+N more)` |
| EC-009 | Mid-stream decode/parse error (truncated/corrupt file N — e.g. killed `tcpdump -G`) | `OtError::StreamInFile { path, inner }` names file N and delegates the inner exit code (Parse → 70, UnsupportedLinkType → 65); `MultiPacketIter` latches terminal (fail-fast). Adversary M-1. |

### Known limitations (accepted, not blocking)

- **Missing intermediate file masked by a later link-type mismatch** (adversary
  m-3): for `analyze A B C` where `A`=ETHERNET, `B`=missing, `C`=LINUX_SLL, the
  homogeneity guard skips the unreadable `B` (deferred to streaming, per the
  AC-003 design) and reports `MixedLinkTypes(A, C)` — the operator is told A/C
  mismatch, not that B is missing. Both are genuine error states and the run
  still fails fast with no report; after fixing the link types the missing-file
  error surfaces. Acceptable.
- **Multi-interface pcapng false-homogeneity** (adversary observation): a single
  pcapng with two IDBs of different link types passes the guard (it peeks only
  the first IDB, per AC-003) and then `decode_block` treats every frame as
  Ethernet (a pre-existing `decode_block` limitation). Tracked as tech-debt for
  a future "full per-interface link-type read" story; not introduced by S-9.01.

## Scrub Stance

### 1. What does this feature extract?

Nothing new. P0-10 changes **how many files** feed the existing ingestion path,
not **what** is parsed from them. The per-packet decode (`decode_ethernet`) and
the observer are unchanged. No new protocol field, hostname, credential, or
identifier is extracted.

### 2. What does this feature render?

- A combined **source label** (basenames only) in the HTML/MD report header
  for the multi-file case (AC-005). Basenames are already considered
  privacy-sensitive and are handled by the F-ADV-P2-009 basename-only rule;
  the multi-file label extends that same rule to N files.
- The audit log's `input_pcaps` array (AC-004) — basenames + sizes + SHA-256s,
  exactly as the single `input_pcap` carried before, one per file.

### 3. What's the BCSI classification?

- **Source filenames:** Medium. Operators name rotated captures with dates and
  sometimes site/line identifiers (`acme-line3-2024-10-01.pcap`). The
  basename-only rule (F-ADV-P2-009) is the existing mitigation; this story
  reuses it verbatim and never emits a full path.
- **Per-file SHA-256 / size:** Low. Hashes are one-way; sizes are non-identifying.
- No High-classification surface is added.

### 4. What's the scrub stance?

- **No new pseudonym class.** Filenames are not scrubbed (they live outside the
  parsed PCAP bytes); they are protected by the basename-only rule, which this
  story preserves for both single- and multi-file paths.
- **Leak detector:** unchanged. The leak detector scans the scrubbed markdown
  fed to the AI; basenames in the report header are already within today's
  posture (the single-file path emits a basename today). No new bytes reach the
  AI provider that didn't before — the AI sees the same scrubbed report
  structure regardless of input file count.
- **Audit log (BC-7.01.003):** `input_pcaps` carries basenames only; the
  no-real-identifier assertion extends across the vec.
- **Test that enforces it:** the existing
  `invariant_no_real_values_reach_ai_provider` test plus an extended audit
  snapshot covering a 2-file `input_pcaps`.

## Architecture Compliance Rules

- **ADR-0008 (sync, no async):** `iter_packets_multi` chains synchronous
  `PacketIter`s. No runtime, no threads.
- **ADR-0004 (owned payloads):** unchanged — each `Packet` still owns its bytes.
- **ADR-0001/0002:** no new parsing dependency. The chain is std-only
  (`std::iter` / a small hand-rolled `MultiPacketIter`); do **not** pull in
  `itertools` just to chain.
- **F-ADV-P2-009 (basename-only):** the multi-file source label and every
  `InputDescriptor.path` MUST be `file_name()` basenames, never full paths.
- **Errors (CLAUDE.md):** add `OtError::MixedLinkTypes` with a `EX_DATAERR`
  (65) exit mapping; the message must suggest the fix (merge only captures of
  the same link type). Do **not** reach for `anyhow`.
- **Effectful boundary:** the new file-reading code lives in `pcap.rs` (the
  established I/O shell), not in the pure core.
- **Panic policy:** `iter_packets_multi` and `peek_link_type` return `Result`;
  never panic on a missing/short/garbage file.
