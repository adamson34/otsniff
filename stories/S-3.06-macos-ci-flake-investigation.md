# S-3.06: Stop the recurring macOS rustup-init/cargo flake in CI

## Narrative

- **As a** maintainer
- **I want** the macOS test job to pass reliably on first attempt
- **So that** every merge to develop and every PR doesn't cost us a 30-second rerun and a context switch

## Status (2026-05-14T17:30 update — investigation report inline)

**ROOT CAUSE CONFIRMED.** After four PRs of empirical investigation,
the cause is documented below. The actual fix is deferred to a future
session under this same story.

### Investigation summary

| Attempt | PR | Hypothesis | Outcome |
|---|---|---|---|
| 1 | #60 (merged) | `macos-latest` (image 15) is buggy; pin macos-14 | Failed — same flake on macos-14 develop pushes |
| 2 | #61 (merged) | PATH resolution wrong; add `$HOME/.cargo/bin` PATH guard | PATH guard *did* resolve cargo correctly on its own step; subsequent Swatinem step broke it |
| 3 | #62 (merged + reverted in #64) | Skip PATH entirely; call `$HOME/.cargo/bin/cargo` directly | Failed — diagnostic showed binary at that path returns `rustup-init 1.29.0`. The cargo file IS rustup-init bytes after cache restore. |
| 4 | #63 (closed) | Re-run `rustup default stable` after Swatinem to repair proxy | Failed — `rustup` at `$HOME/.cargo/bin/rustup` is also rustup-init bytes. Every binary in that directory is corrupted; no in-band repair available. |

### Root cause

`Swatinem/rust-cache@v2`'s cache restore step on macOS replaces ALL
binaries under `$HOME/.cargo/bin/` (cargo, rustc, rustup, rustdoc, etc.)
with copies of the `rustup-init` installer binary. Likely cause: the
cache content was captured during a prior run where the proxy was in
a degraded state (e.g., during initial install), and once a bad cache
is published, every subsequent run that hits cache-key match restores
the bad state. PR runs typically start with an empty cache and succeed;
develop pushes hit the populated bad cache and fail.

No in-band fix is possible from within the workflow because the binaries
needed to *repair* the situation (`rustup`, `cargo`) are themselves the
corrupted ones.

### Remaining viable paths

Both deferred to a future cycle:

- **Option (b''):** Drop `Swatinem/rust-cache@v2` on the macOS job only.
  Adds ~90 seconds per macOS run for cold compile; eliminates the
  cache-corruption vector entirely.
- **Option (c):** Replace `dtolnay/rust-toolchain@stable` +
  `Swatinem/rust-cache@v2` with `actions-rust-lang/setup-rust-toolchain`,
  which manages its own caching strategy and reportedly avoids this
  failure mode.

### Current state on develop

| Layer | Status |
|---|---|
| PR #60 (macos-14 pin) | Kept; inert in failing case but harmless |
| PR #61 (PATH guard + diagnostic) | Kept; diagnostic output remains valuable for future debugging |
| PR #62 (absolute-path call) | Reverted via PR #64 — the absolute-path attempt removed the rerun-clears-it workaround so develop pushes always failed |
| PR #63 (rustup-default repair) | Closed without merge — repair tool is itself corrupted |
| PR #64 (revert) | Merged; current develop state |

Develop is back to the bare `cargo test` invocation that at least
sometimes clears on rerun. PR CI always passes (empty cache). Develop
pushes intermittently fail and are manually rerun-cleared.

The story stays open in the v0.4.1-patch backlog. Status:
`in_progress → deferred (investigation complete; fix deferred to v0.4.1)`.

## Why now / why deferred

**Observed signal (updated 2026-05-14):** Hit 3× in 48 hours
(2026-05-13 on PR #58 CI; 2026-05-14 on the develop push after #58;
2026-05-14 on the develop push after #59 merge). Failure mode identical
all three times:

```
error: error: unexpected argument 'test' found
Usage: rustup-init[EXE] [OPTIONS]
```

`dtolnay/rust-toolchain@stable` successfully installs the toolchain
(`info: using existing install for stable-aarch64-apple-darwin`,
`info: default toolchain set to stable-aarch64-apple-darwin`) but the
next step's `cargo test` invocation resolves `cargo` → `rustup-init`
binary rather than the cargo proxy. Manual rerun clears it every time.

**Why deferred to v0.4.1-patch:** 30s rerun cost is below the bar for
interrupting Wave 1 detector work. Two hits is a pattern but not yet
an emergency — the build-out backlog (S-2.05..S-2.11 detectors) carries
more user value per point than CI surgery.

## Acceptance Criteria

### AC-001 (root-cause investigation, write-up)

- Investigation note committed under `docs/ci-investigations/2026-05-macos-rustup-flake.md`
  documenting:
  - Which `macos-latest` image versions were running at each flake
    occurrence (GitHub publishes the image label in the runner setup
    logs)
  - Whether the failure correlates with the runner image transition
    from macOS 14 → 15 (current hypothesis)
  - Whether other Rust projects on GitHub Actions have reported the
    same symptom (link upstream issues in dtolnay/rust-toolchain,
    actions/runner-images, or rust-lang/rustup if found)
- The note ends with a one-sentence root cause hypothesis and a
  recommended fix.

### AC-002 (apply chosen fix)

Pick exactly one of the following (justify in the investigation note):

- **(a) Pin runner image.** `runs-on: macos-latest` → `runs-on: macos-14`.
  Trade-off: pins to an older image; macos-14 is GA-supported until at
  least 2027 per GitHub's image lifecycle.
- **(b) Insert PATH/env normalization step.** Add a step between
  `dtolnay/rust-toolchain` and `cargo test` that runs
  `source "$HOME/.cargo/env" && which cargo && cargo --version` to
  force the cargo proxy into the shell's lookup path before invocation.
- **(c) Switch rust-toolchain action.** Replace `dtolnay/rust-toolchain@stable`
  with `actions-rust-lang/setup-rust-toolchain@v1` (the rust-lang
  org maintained alternative) if AC-001 finds an upstream fix landed
  in the newer action.

**Test:** After the fix lands, kick 5 consecutive CI runs on develop
(empty commits or workflow_dispatch). All 5 macOS jobs pass without
rerun. Document the run IDs in the investigation note.

### AC-003 (rollback plan)

If the chosen fix causes a different macOS regression, the investigation
note documents how to roll back (single-commit revert) and why the
next fallback option from the list above is the preferred next attempt.
