# S-13.01: Extract privacy/scrub layer into `crates/otsniff-privacy`

## Narrative

- **As a** maintainer building a second product (the planned AI-powered
  OT threat-hunting tool, "otsniff-hunt") as an additional workspace crate
  in this repo
- **I want** the pseudonym scrub/unscrub mechanics and the fail-closed leak
  detector available as a standalone, otsniff-independent crate
- **So that** otsniff-hunt can reuse the exact same never-see-real-identifiers
  guarantee over data it discovers from sources otsniff never touches (platform
  APIs, threat feeds, otsniff's own JSON output), without duplicating or
  forking the verified privacy core

## Context — what already exists

The privacy layer already splits cleanly into two halves inside
`src/scrub.rs` (1444 lines) and `src/ai/leak_detector.rs` (731 lines):

1. **Population** — `build_map`, `build_map_at`, `merge_map` — walk otsniff's
   `Observations`/`HostObs` capture model to *discover* identifiers. This is
   otsniff-specific: otsniff-hunt has no `Observations` and will populate a
   `ScrubMap` from different sources entirely.
2. **Mechanics** — `ScrubMap` (struct + impl), `scrub_text`, `unscrub_text`,
   `pseudonym_regex`, `merge_family`, `max_index`, `is_canonical_pseudonym`,
   `parse_pseudonym_index`, and all of `leak_detector.rs` — pure functions over
   `BTreeMap<String, String>` and `&str`, with no otsniff-specific type in
   their signatures.

This story implements ADR-0016's decision: move (2) into a new workspace
crate `crates/otsniff-privacy`, following the exact precedent ADR-0013 set for
`crates/zonewarden` (pure formally-verified core → workspace crate, not a
plain `src/` module, so the Kani-proof-relevant no-I/O boundary is enforced by
`cargo`'s dependency graph rather than by convention).

**This is a pure refactor.** No behavioral contract's meaning changes; every
BC listed in frontmatter is preserved exactly, just proved/tested against code
that now lives in a different crate. There is no new user-facing behavior and
no CLI surface change.

### AC-003 — Error boundary preserves message shape and exit code (traces to BC-5.02.003, F-ADV-P2-007)

- `otsniff-privacy` defines its own error type, e.g.:
  ```rust
  #[derive(thiserror::Error, Debug)]
  pub enum PrivacyError {
      #[error("{kind}: {message}")]
      Leak { kind: String, message: String },
      #[error("{message}")]
      MapCorrupt { message: String },
  }
  ```
  `Leak` covers what `OtError::PrivacyLeak` covered (the fail-closed leak
  detector). `MapCorrupt` is a second, distinct variant added during
  implementation for `ScrubMap::validate()`/`merge_family()`'s structural
  map-corruption checks (empty pseudonym/real value, non-canonical
  pseudonym shape, duplicate real value, pseudonym collision) — pre-move
  these were `OtError::Parse`, a data-integrity fault, not a privacy-invariant
  trip. Keeping them distinct from `Leak` matters: a corrupted map's
  diagnostic message legitimately names the offending real value (that's
  the point of the diagnostic), which must never happen under a
  `"privacy invariant tripped"` label whose whole meaning is "no raw value
  present."
- `otsniff`'s `src/error.rs` replaces the inline
  `PrivacyLeak { kind: String, message: String }` variant with:
  ```rust
  #[error("privacy invariant tripped: {0}")]
  Privacy(otsniff_privacy::PrivacyError),
  ```
  wrapped via a **hand-written `From` impl**, not `#[from]` — a literal
  `#[from]` derive also derives `#[source]`, and `src/main.rs` walks
  `Error::source()` to print `caused by:` lines, so `#[from]` would add a
  new stderr line that didn't exist pre-extraction (an AC-005 violation).
  The hand-written impl routes `PrivacyError::Leak` to `OtError::Privacy`
  (exit 75, unchanged) and `PrivacyError::MapCorrupt` to `OtError::Parse`
  (exit 70, preserving its pre-extraction shape exactly). See
  `docs/adr/0016-otsniff-privacy-crate.md`'s "Decision refinement" section
  for the full rationale.
- `OtError::exit_code()`'s `Self::Privacy(_) => 75` replaces the old
  `Self::PrivacyLeak { .. } => 75` arm for the `Leak` case; `MapCorrupt`
  routes to the existing `Self::Parse(_) => 70` arm — exit codes are
  unchanged for both original call-site classes.
- **Test (regression, moved from `error.rs`/`leak_detector.rs`):**
  `ensure_clean("see 10.0.0.5")` still produces an `OtError` whose
  `.to_string()` contains `"privacy invariant tripped"` and `"IPv4"`, does
  **not** contain `"10.0.0.5"` (F-ADV-P2-007), contains `"hash-prefix"`, and
  whose `.exit_code()` is `75`.
- **Test (regression):** the hostname-leak test (`ensure_no_map_values`
  catching `"LINE-3-PLC"` that regex misses) produces the same message
  shape and exit code through the new wrapper.

### AC-004 — otsniff's population logic and all call sites still compile and pass (traces to BC-5.03.001)

## Forbidden Dependencies

- `otsniff-privacy` must NOT depend on `otsniff` (the root binary crate) —
  that would invert the dependency direction and make the crate useless to a
  second consumer.
- `otsniff-privacy` must NOT depend on `zonewarden` — the two extracted crates
  are independent; nothing in the privacy layer needs segmentation types.
- `otsniff-privacy` must NOT depend on `askama`, `pcap-parser`, `etherparse`,
  `clap`, `ipnet`, `pulldown-cmark`, or `serde_norway` — none of these are used
  by the moved code; pulling any of them in is a sign a population-side
  function was moved by mistake.
