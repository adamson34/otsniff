# S-11.01: Diff capture-window normalization

## Narrative

- **As an** analyst running `otsniff diff baseline.pcap current.pcap` on two
  recordings of unequal duration (e.g. a 1h baseline vs a 30min current)
- **I want** the flow-shift detector to compare per-second rates, not raw byte
  counts, and to warn me when the two capture windows differ materially
- **So that** every steady-state flow isn't reported as a 2× "shift" that is
  really just a duration artifact, drowning the real behavioral changes

## Acceptance Criteria

### AC-001 — Per-side capture-window duration (traces to BC-3.08.004 precondition)

In `src/diff.rs::compute_with_multiplier`, derive each side's capture-window
duration from its `Observations` (using `min_ts`/`max_ts`, added in S-10.01):

```rust
fn window_secs(obs: &Observations) -> Option<f64> {
    match (obs.min_ts, obs.max_ts) {
        (Some(min), Some(max)) => {
            let s = (max - min).num_milliseconds() as f64 / 1000.0;
            if s >= 1.0 { Some(s) } else { None }   // <1s ⇒ degenerate, can't normalize
        }
        _ => None,
    }
}
```

A window that is missing, zero, or sub-second (the S-10.01 degenerate cases) is
**`None`** — not a usable normalization denominator.

### AC-002 — Rate-normalized flow-shift ratio (traces to BC-3.08.004 postcondition)

For a flow present in BOTH captures, when **both** sides have a usable window
(`Some`), the flow-shift ratio is computed on **rates** (bytes/sec):

```
base_rate = baseline_bytes / base_window_secs
curr_rate = current_bytes  / curr_window_secs
(hi, lo)  = (max(base_rate, curr_rate), min(base_rate, curr_rate))
ratio     = hi / lo          // flagged when ratio >= multiplier
```

- `FlowDelta.ratio` becomes this **rate ratio**; `baseline_bytes`/`current_bytes`
  stay the raw observed counts (for display). The `lo == 0` skip still applies
  (on the rate).
- **Fallback:** when **either** side's window is `None` (degenerate), normalization
  is impossible — fall back to the existing **raw byte ratio** (current behavior,
  unchanged) so the detector still works.
- New `Diff` fields record what happened:
  - `rate_normalized: bool` — `true` iff rates were used.
  - `baseline_window_secs: Option<f64>`, `current_window_secs: Option<f64>` — the
    per-side durations (for the warning, banner, and JSON consumers).
- **Worked example (the motivating case):** a steady flow with
  `baseline_bytes = 2·X` over a 3600s window and `current_bytes = X` over a 1800s
  window. Raw ratio = 2.0 (flagged at the 2× default). Rate ratio =
  `(2X/3600) / (X/1800)` = `(X/1800)/(X/1800)` = **1.0** → **not** flagged. The
  duration artifact is gone.
- **Tests:** unit test the worked example (raw flags it, rate does not); a flow
  whose *rate* genuinely doubled IS still flagged; degenerate-window input falls
  back to raw and still flags a 2× byte change.

### AC-003 — Capture-window-mismatch warning on stderr (traces to BC-3.08.005)

`src/cli.rs::run_diff`: after `compute`, emit a stderr `WARNING:` when the
windows are problematic, with text that reflects the normalization outcome:

- **Degenerate (could not normalize):** when `rate_normalized == false` because a
  side's window is `None` →
  `WARNING: a capture window is missing or sub-second; flow-shift ratios are raw byte counts and may be duration artifacts`.
- **Normalized but mismatched:** when `rate_normalized == true` AND the two
  windows differ by 2× or more (`max/min >= 2.0`) →
  `WARNING: capture windows differ {N}× (baseline {B}s vs current {C}s); flow-shift ratios are rate-normalized (bytes/sec)`.
- **Comparable + normalized** (windows within 2×): no warning.

Mirrors the existing guard/capture-sanity stderr pattern (`eprintln!("WARNING: …")`).

### AC-004 — Diff-report banner (traces to BC-3.08.005)

When a window-mismatch/degenerate condition holds (same trigger as AC-003), the
diff HTML and markdown reports render a banner (mirroring the existing
`no-deltas-banner`) stating the window sizes and whether flow-shift ratios are
rate-normalized or raw. When windows are comparable and normalized, **no banner**
is emitted (so a normal diff is unchanged except for the now-rate-based ratios).

- HTML: `templates/diff.html` — a `window-mismatch-banner` div, conditional.
- MD: `src/report_md.rs::render_diff_markdown` — a blockquote line, conditional.
- The diff header also shows a one-line `Capture windows: baseline {B}s vs current {C}s` when both are known (informational, always when present).

### AC-005 — Output changes are intentional & reviewed

This story **intentionally** changes diff output: `FlowDelta.ratio` is now a rate
ratio (when normalized), the flagged-flow set changes (fewer duration-artifact
shifts), and the new `Diff` fields + banner appear. All affected diff snapshots
(`tests/snapshot.rs` diff cases + any `s_6_02`/diff integration snapshots) are
updated via `cargo insta review`. Non-diff snapshots (analyze HTML/MD/JSON) are
**unaffected** and must stay green unmodified.

## Scrub Stance

### 1. What does this feature extract / render?

Nothing new from packet content. It reads packet **timestamps** (already
observed, via `min_ts`/`max_ts`) to compute per-side durations, and renders
durations (seconds, a number) + a rate ratio + constant-English warning text. No
IP/MAC/hostname is read or emitted.

### 2. BCSI classification

**None new.** Durations and rates are non-identifying numbers; the warning text
is constant English. Flow endpoints in `FlowDelta`/`FlowSummary` are already
pseudonymized by the existing diff path (resolved through the merged `ScrubMap`)
— this story does not change endpoint handling.

### 3. Scrub stance

- No new pseudonym class, no new BCSI surface. Durations/rates/warnings carry no
  identifiers; the leak detector posture is unchanged. The diff's existing
  pseudonymization of endpoints is untouched.

## Architecture Compliance Rules

- **Pure core:** `compute_with_multiplier` stays pure (no I/O); duration math is
  `chrono` arithmetic on already-observed timestamps.
- **No new dependencies** (`chrono` already present).
- **ADR-0003:** the HTML banner uses a pre-formatted view field + conditional
  template block; no custom filter.
- **Determinism:** rate computation is deterministic; sort orders unchanged.
  Guard against `NaN`/`inf` — never divide by a zero/`None` window (that path
  falls back to raw); `lo == 0` skip retained.
- **No regression to non-diff output:** analyze/scrub snapshots must not change.

## Edge Cases

| ID | Scenario | Expected |
|----|----------|----------|
| EC-001 | Equal windows (both 1800s) | Rate ≡ byte ratio; results unchanged in spirit; `rate_normalized = true`; no warning/banner |
| EC-002 | 1h baseline vs 30min current, steady flows | Rate ratio ≈ 1.0 → not flagged; banner + WARNING about the 2× window difference |
| EC-003 | One side degenerate (sub-second / all-epoch / no ts) | Fall back to raw ratio; `rate_normalized = false`; degenerate WARNING + banner |
| EC-004 | Both sides degenerate | Raw ratio; degenerate WARNING + banner |
| EC-005 | A flow whose true rate doubled (same windows) | Still flagged (rate ratio ≥ 2×) — real shift preserved |
| EC-006 | A flow present on one side only | Unchanged — goes to `flows_new`/`flows_gone`, not rate-normalized |
| EC-007 | `lo` rate == 0 (one side zero bytes on a both-sides key) | Skipped (as today), no div-by-zero |
| EC-008 | Windows differ exactly 2× | `>= 2.0` is inclusive, so exactly 2× (the 1h-vs-30min motivating case, EC-002) DOES trigger the mismatch warning/banner. Windows differing by *less than* 2× are silent but still rate-normalized; the flow-shift table carries the rate-note so a flagged flow isn't misread. (Adversary pass-2 M-1: aligned the threshold to `>= 2×`, matching the narrative + the flow-shift detector's `>=` multiplier.) |

### Known limitations (accepted)

- **Whole-capture-window denominator** (adversary LOW-2): `window_secs` uses the
  whole-capture `min_ts`/`max_ts`, not each flow's *active* span. A non-steady
  (bursty) flow that moved the same bytes in the same real burst in both captures
  can be newly flagged when the surrounding capture windows differ, because its
  whole-capture rate differs. Truly steady flows — the motivating case — are
  handled correctly. The whole-capture denominator is the spec's deliberate
  choice (per-flow active-span normalization is a larger feature). Tracked as
  `TD-S1101-001`. The rate-note + window banner make the basis explicit so the
  operator can judge.
