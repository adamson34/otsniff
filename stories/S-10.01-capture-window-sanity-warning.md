# S-10.01: Capture-window sanity warning

## Narrative

- **As an** analyst handed a PCAP whose timestamps are degenerate (all-zero /
  epoch 1970, sub-second window, or non-monotonic ordering — e.g.
  `iFix_Server119.pcap` and `MicroLogix56.pcap`, which ship with all-zero
  timestamps)
- **I want** otsniff to flag the bad time base in the report header and on
  stderr
- **So that** I know any time-dependent result (capture-source heuristic, flow
  rate, port-scan window, capture-window display) may be unreliable, instead of
  silently trusting `Capture window: 1970-01-01 00:00:00 → 1970-01-01 00:00:00`

## Acceptance Criteria

### AC-001 — Observer timestamp tracking (supports BC-4.01.004)

`src/observe.rs`: `Observations` gains three fields, all maintained in
`observe()` once per packet:

- `min_ts: Option<DateTime<Utc>>` — running minimum of `pkt.ts`.
- `max_ts: Option<DateTime<Utc>>` — running maximum of `pkt.ts`.
- `timestamps_monotonic: bool` — initialized `true`; set `false` the first time
  a packet's `ts` is strictly less than the immediately preceding packet's `ts`.

`first_ts` / `last_ts` are **unchanged** (still first/last *processed* packet —
they drive the existing "Capture window" display; do not repoint that display at
min/max, to avoid output churn). If `Observations` does not already carry a
total packet count usable by the detector, add `packet_count: u64`.

- **Tests:** observer fed a monotonic 3-packet sequence → `timestamps_monotonic
  == true`, `min_ts == first packet ts`, `max_ts == last packet ts`; observer
  fed an out-of-order sequence (p2.ts < p1.ts) → `timestamps_monotonic == false`,
  `min_ts`/`max_ts` still the true extremes.

### AC-002 — Pure sanity detector (traces to BC-4.01.004)

New module `src/capture_sanity.rs` (pure-core, sibling to `capture_source.rs`):

```rust
pub enum CaptureWarning {
    EpochZeroTimestamps,
    SubSecondWindow,
    NonMonotonicTimestamps,
}
impl CaptureWarning { pub fn message(&self) -> &'static str { /* stable text */ } }

pub fn assess(obs: &Observations) -> Vec<CaptureWarning>;
```

Rules (evaluated in this fixed order so the output `Vec` is deterministic):

1. **`EpochZeroTimestamps`** — there is ≥1 packet and `max_ts <= UNIX_EPOCH`
   (i.e. `max_ts.timestamp() <= 0`): every packet sits at/before epoch second 0,
   so there is no real time base (covers all-zero legacy captures and pcapng
   SimplePacket captures, which carry no timestamp).
2. **`SubSecondWindow`** — NOT epoch-zero, `packet_count >= 2`, and
   `max_ts - min_ts < Duration::seconds(1)`.
3. **`NonMonotonicTimestamps`** — `obs.timestamps_monotonic == false`.

- Returns an **empty `Vec`** when the time base is sane (multi-second,
  monotonic, post-epoch) or when there are no timestamps at all
  (`min_ts`/`max_ts` are `None` → the report already shows "(no timestamps)";
  no warning added).
- Pure: no I/O, no panic; `message()` returns a stable human-readable string per
  variant (e.g. `EpochZeroTimestamps` → `"capture has no real timestamps (all at/before the Unix epoch); time-based findings are unreliable"`).
- **Tests (inline):**
  - all-epoch capture → `[EpochZeroTimestamps]`
  - 3 packets spanning 0.4s (post-epoch, monotonic) → `[SubSecondWindow]`
  - out-of-order packets spanning minutes → `[NonMonotonicTimestamps]`
  - out-of-order AND sub-second → `[SubSecondWindow, NonMonotonicTimestamps]`
  - sane multi-second monotonic capture → `[]`
  - exactly-1.0s window (boundary) → `[]` (strict `< 1s`)
  - single post-epoch packet → `[]` (SubSecond needs ≥2 packets)
  - empty observations (no packets) → `[]`

### AC-003 — Report banner, only when degenerate (traces to BC-4.01.005)

- `src/report.rs`: `ReportView` gains `capture_warnings: Vec<String>`
  (pre-formatted messages — ADR-0003). `render_html` computes
  `capture_sanity::assess(obs)` and maps each to `.message()`.
- `templates/report.html`: render a warning banner **only when**
  `capture_warnings` is non-empty (`{% if capture_warnings.len() > 0 %}` … loop
  … `{% endif %}`), placed right after the `capture-meta` window line, with a
  dedicated CSS class (e.g. `.capture-warning`). When the vec is empty, **no new
  markup is emitted** → existing clean-capture HTML snapshots stay byte-identical.
- `src/report_md.rs`: when `assess(obs)` is non-empty, write a
  `> ⚠ **Capture timestamp warning:** <msg>; <msg>` blockquote line after the
  "Capture window" line; when empty, write nothing → existing MD snapshots
  unchanged.
- **Tests:** a snapshot for a degenerate-timestamp fixture (e.g. all-epoch)
  shows the banner in both HTML and MD; existing clean snapshots remain green
  **without modification** (this is the regression lock for AC-005).

### AC-004 — stderr WARNING, mirroring the guard-warning pattern (traces to BC-4.01.005)

- `src/cli.rs`: in `run_analyze` and `run_scrub`, after `analyze()` returns,
  emit one `eprintln!("WARNING: {msg}")` per `capture_sanity::assess(obs)` entry
  — mirroring `classify_with_guard`'s existing
  `if let Some(warning) = classification.guard_warning() { eprintln!("WARNING: {warning}") }`.
  Emitted **always** (not gated on `--verbose`): it is a data-quality signal the
  operator must see. A sane capture emits no such line.
- **Tests (`tests/cli_smoke.rs`):**
  - `analyze` on a degenerate-timestamp fixture prints `WARNING: ...` (matching
    the capture-sanity text) to stderr, exit 0
  - `analyze` on a normal fixture prints no capture-sanity WARNING

### AC-005 — Sane captures are byte-identical (traces to BC-4.01.005 invariant)

A capture with monotonic, multi-second, post-epoch timestamps produces
byte-identical HTML / MD / JSON to pre-S-10.01 and emits no capture-sanity
stderr line. Satisfied by: existing report/MD/JSON snapshots remaining green
unmodified + the `assess() == []` unit test on a sane fixture.

## Scrub Stance

### 1. What does this feature extract / render?

Nothing new from packet *content*. It reads only packet *timestamps* (already
observed) and renders human-readable, non-identifying warning strings
(`"capture has no real timestamps …"`). No IP/MAC/hostname is read or emitted by
this feature.

### 2. BCSI classification

**None.** The warning messages are static English describing the time base; they
contain no asset identifiers. The banner sits alongside the existing
already-rendered "Capture window" line.

### 3. Scrub stance

- **No new pseudonym class, no new BCSI surface.** The messages are constant
  strings selected by `CaptureWarning` variant; they never interpolate observed
  values. They are therefore inert with respect to the scrub layer and the leak
  detector.
- **AI path:** the warning strings are part of the rendered markdown; being
  constant English with no identifiers, they pass the leak detector unchanged
  and add no real values. The existing
  `invariant_no_real_values_reach_ai_provider` test continues to hold.

## Architecture Compliance Rules

- **ADR-0003:** the HTML banner uses a **pre-formatted `Vec<String>`** on the
  view struct; no custom askama filter. The template only iterates + conditionally
  renders.
- **New module justification:** `capture_sanity.rs` is a pure sibling of
  `capture_source.rs` (same shape: an enum + a pure function over `Observations`,
  plus `message()` like `Classification::report_line`/`guard_warning`). Keeping it
  separate from `capture_source.rs` preserves the SPAN/TAP heuristic's focus.
- **No new dependencies.** Uses `chrono` (already present) for the epoch constant
  and `Duration`.
- **Panic policy:** `assess` never panics on any `Observations` (including
  empty / `None` timestamps).
- **Output stability:** clean captures must be byte-identical — the banner/line
  is emitted **only** when `assess` is non-empty. Any snapshot change beyond the
  new degenerate-fixture snapshots is a bug.

## Edge Cases

| ID | Scenario | Expected |
|----|----------|----------|
| EC-001 | pcapng with only SimplePacket blocks (ts 0,0) | `EpochZeroTimestamps` (no real time base) |
| EC-002 | single post-epoch packet | `[]` — no SubSecond (needs ≥2), no epoch, monotonic |
| EC-003 | window exactly 1.000s | `[]` — strict `< 1s` boundary |
| EC-004 | timestamps step backward by a tiny amount (reorder / clock skew) | `NonMonotonicTimestamps` (any backward step counts) |
| EC-005 | multi-file analyze with files passed out of chronological order (TD-S901-002) | `NonMonotonicTimestamps` fires → the banner now *explains* the inverted window display |
| EC-006 | all-epoch capture | banner shows the epoch message; window line still renders "1970… → 1970…" (unchanged) |
| EC-007 | sane multi-second monotonic capture | no banner, no stderr line, byte-identical output |
| EC-008 | capture with no decodable timestamps at all (`min_ts`/`max_ts` None) | `[]` — report already shows "(no timestamps)"; no double-signal |
