# S-6.01: Stable pseudonym maps across captures (`merge_map` operation)

## Narrative

- **As an** analyst doing longitudinal triage on quarterly captures
  of the same network
- **I want** pseudonym maps that are stable across captures (same real
  IP → same `host_NNN`)
- **So that** the upcoming `diff` subcommand can compare apples to apples

## Acceptance Criteria

### AC-001 (BC-5.03.001 — merge_map)
- `scrub::merge_map(baseline: ScrubMap, current: &Observations) -> ScrubMap`:
  - For every real identifier already in `baseline`, the existing
    pseudonym is reused.
  - New identifiers in `current` are appended with fresh pseudonyms,
    counter starting at `baseline.max_index + 1`.
  - Returns a merged map containing all identifiers from both.
- **Test:** Property test: merge is associative; merging an empty map
  is the identity.

### AC-002 (round-trip remains exact)
- After merge, `unscrub(scrub(text, merged), merged)` still equals `text`
  for any text containing real identifiers from baseline OR current.
- **Test:** Existing scrub round-trip tests cover this; add one fixture
  that exercises both old and new pseudonyms in the same text.

### AC-003 (CLI surface)
- `otsniff scrub <pcap> --baseline-map old.map.json -o report.md --map new.map.json`
  produces `new.map.json` that strictly extends `old.map.json` per AC-001.
- `otsniff scrub <pcap> -o report.md --map new.map.json` (no baseline)
  preserves current behavior.

### AC-004 (leak detector survives merge)
- A leak detector pass over text scrubbed with a merged map still
  passes; no path lets a real identifier slip through after merge.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Baseline map has corrupted pseudonym (e.g., `host_001` mapped to nothing) | Reject map at load time with OtError |
| EC-002 | Same pseudonym name used for two different real values across baseline and current | Impossible if AC-001 holds; assert + bug if reached |
| EC-003 | Baseline has identifiers no longer in current | Preserve; future story may decide whether to retain or prune |
