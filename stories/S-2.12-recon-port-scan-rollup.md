# S-2.12: Roll up `recon.port_scan` by scanning source IP

## Narrative

- **As an** analyst running otsniff on a real plant capture
- **I want** one `recon.port_scan` finding per scanning source host —
  summarizing port-spread + dst-spread — instead of one finding per
  `(src, dst_port, proto)` tuple
- **So that** a single attacker / scanner doesn't generate thousands of
  finding cards and the report stays exec-readable

## Real-PCAP evidence (regression that motivates this story)

Running v0.4.0-dev develop tip against
`tests/fixtures/4SICS-GeekLounge-151022.pcap` (4SICS public capture,
200 MB, 2.25M packets, 99 hosts, 640k flows):

```
Total findings:  26,075
  - recon.port_scan:  26,067  ← bug
  - All 8 other rules combined:  8
Report size:  63 MB HTML (unfit for exec readability)
```

The 26k cardinality is correct per S-2.10's spec (the detector grouped
by `(src, dst_port, proto)` and 192.168.2.22 was scanning EVERY port).
But the desired output is **one finding** per scanning source IP, with
the port-spread + dst-spread as evidence — not 25k findings for the
same attacker.

## Acceptance Criteria

### AC-001 (BC-3.05.006 — primary grouping is source IP, not (src, port, proto))

`src/findings/recon_scan.rs::detect` groups observations by source IP.
For each source, it computes:

- `distinct_dsts: BTreeSet<IpAddr>` — distinct destinations contacted
- `distinct_ports: BTreeSet<(u16, u8)>` — distinct `(dst_port, proto)` pairs
- `total_flows: usize` — count of flows in this src's set

A finding fires per source when EITHER:
- `distinct_dsts.len() >= DST_THRESHOLD` (horizontal scan), OR
- `distinct_ports.len() >= PORT_THRESHOLD` (vertical scan)

Constants tuned for real OT captures:
```
DST_THRESHOLD = 10       // horizontal: 1 src → many dsts
PORT_THRESHOLD = 10      // vertical: 1 src → many ports
HIGH_THRESHOLD_DST = 50  // High severity escalation
HIGH_THRESHOLD_PORT = 50 // High severity escalation
```

Severity rules:
- `distinct_dsts >= HIGH_THRESHOLD_DST` OR `distinct_ports >= HIGH_THRESHOLD_PORT` → **High**
- Otherwise → **Medium**

- **Test:** Synthetic fixture with 1 src hitting 12 dsts on 8 ports → emits exactly ONE finding (not 8 or 96).

### AC-002 (BC-3.05.006 — evidence summarizes the scan pattern)

The single finding's evidence rows summarize what the source did. Pseudo-shape:

```
Source 192.168.2.22 (Cisco) scanned:
  - 16 distinct destinations
  - 4,127 distinct (port, proto) combinations
  - Classification: combined (horizontal + vertical)
  - Top destinations: 192.168.88.15, 192.168.88.25, 192.168.88.30, ... (cap 15)
  - Sample ports: 0, 1, 3, 8, 22, 80, ... (cap 15)
  - Total flows: 18,432
```

The finding title is e.g.:
> `Port scan: 192.168.2.22 probed 16 hosts across 4,127 (port, proto) combinations`

- **Test:** A test asserts the rendered finding has evidence rows
  mentioning BOTH "16 distinct destinations" AND a `(port, proto)`
  count.

### AC-003 (BC-3.05.006 — broadcast/multicast suppression preserved)

The existing skip-list from S-2.10 (`is_broadcast_or_multicast` —
0.0.0.0, 255.255.255.255, IPv4 224.0.0.0/4, IPv6 ff00::/8) continues
to filter out non-scan destinations from the dst count.

- **Test:** Synthetic fixture with 1 src → 50 multicast dsts only →
  zero findings (below threshold once multicast is filtered).

### AC-004 (data-shape guard — finding count bound is testable)

For the 4SICS-22 capture (gitignored — test is gated on its presence
the same way the existing fixture-dependent tests work), `recon.port_scan`
emits ≤ 20 findings total (not 26,000+).

- **Test:** `tests/cli_smoke.rs` adds a fixture-gated regression test:
  if `tests/fixtures/4SICS-GeekLounge-151022.pcap` exists, run analyze
  against it, assert the JSON output contains `<= 20` findings with
  `id == "recon.port_scan"`. Skip cleanly if the fixture isn't present.

### AC-005 (BC-INDEX updated)

Add `BC-3.05.006 recon.port_scan rolls up per scanning source IP
(supersedes BC-3.05.005 (src, port, proto) grouping)` to BC-INDEX on
factory-artifacts. Mark BC-3.05.005 as "superseded by BC-3.05.006 in
v0.4.1" (do not delete — append-only per project policy).

### AC-006 (existing S-2.10 snapshot tests updated)

The S-2.10 snapshot tests in `tests/snapshot.rs` need to be revised to
match the new grouping:
- `recon_port_scan_fires_at_threshold` — still works conceptually but
  now expects 1 finding per source, not 1 finding per
  `(src, port, proto)`.
- `recon_port_scan_separates_by_port` — REMOVED or REWRITTEN. The new
  behavior is the opposite: same src across different ports → ONE
  finding, not two.
- New test: `recon_port_scan_classifies_horizontal_vertical_combined`

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Source hits 11 dsts on 1 port | Horizontal scan; ONE finding; severity Medium |
| EC-002 | Source hits 1 dst on 12 ports | Vertical scan; ONE finding; severity Medium |
| EC-003 | Source hits 60 dsts on 60 ports | Combined scan; ONE finding; severity High |
| EC-004 | Source hits 5 dsts on 5 ports (below both thresholds) | No finding |
| EC-005 | Two sources each scanning | TWO findings, one per source |
| EC-006 | Legitimate Modbus master polling many slaves on tcp/502 | If ≥10 slaves → fires Medium. False positive accepted — operator validates via the playbook (S-2.10's playbook stays). This is documented as a known false-positive shape; severity-Medium is the right hand-off for "investigate this." |
