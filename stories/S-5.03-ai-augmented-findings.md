# S-5.03: AI-augmented findings — second LLM pass anchored on rules + inventory

> **Dependency rationale:** Hard-depends on three rule stories
> (S-2.05 LDAP, S-2.06 NTLMv1, S-2.07 weak TLS) to give the LLM real
> anchor diversity beyond what already shipped in v0.3. The other four
> Wave-1 detection stories (S-2.08..2.11) are **soft preferences** —
> S-5.03 ships richer if they've landed but does not block on them.

## Narrative

- **As an** OT defender who runs `analyze --ai`
- **I want** a structured "AI-augmented findings" section listing
  patterns the rule layer missed, each with confidence + reasoning
- **So that** the AI's value adds to rule findings instead of duplicating them

## Acceptance Criteria

### AC-001 (BC-6.05.001 — augment request)
- After `run_all_findings` and `build_inventory` produce their outputs,
  a new `augment_findings(observations, findings, inventory) -> Vec<AugmentedFinding>`
  function is called when `--ai` is set.
- Implementation calls a new `AiProvider::augment` method (or extends
  the existing `analyze`) with a distinct prompt template.
- Input bytes are scrubbed; leak detector applies; audit log records.
- **Test:** Mock provider test ingests a fixture, returns a known
  augmented-findings response, asserts shape.

### AC-002 (BC-6.05.002 — response shape)
- `AugmentedFinding { id: String, severity: Severity, title: String,
  evidence: Vec<EvidenceRow>, confidence: Confidence, reasoning: String }`.
- IDs are namespaced `ai.<short>` (e.g., `ai.gateway_inference`,
  `ai.role_misclass`).
- The LLM is asked to return JSON; the parser tolerates pre/post-amble
  text by extracting the first valid JSON array.

### AC-003 (BC-6.05.003 — dedup against rule findings)
- If an augmented finding's evidence overlaps substantially with an
  existing rule finding, the rule finding takes precedence and the
  augmented finding is dropped (or attached as a note).
- **Test:** Fixture where rule fires AND AI suggests same issue → only rule finding in output.

### AC-004 (BC-3.07.001 — render section)
- HTML report has a dedicated "AI-augmented findings" section after
  the rule findings, visually distinguished (color or icon).
- Markdown report has equivalent section.
- The unscrub layer applies to reasoning text before rendering.

### AC-005 (privacy invariant extends)
- The augmented-findings prompt path is covered by the existing
  `invariant_no_real_values_reach_ai_provider` sentinel test.
- A new test variant exercises the augment path specifically.

### AC-006 (audit log records)
- The audit log for `--ai` runs records the augment-pass SHA-256s
  separately from the analyze-pass SHA-256s.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Claude returns malformed JSON | Parser falls back to "no augmented findings" + log warning |
| EC-002 | Claude returns >100 augmented findings | Cap at top-N by confidence; document the cap |
| EC-003 | Augmented finding references a host not in inventory | Drop with logged warning |
| EC-004 | Augment-pass fails after analyze-pass succeeded | Report renders without augment section; the augment error propagates as `OtError::Parse(reason)` (the same variant `ClaudeCliProvider::analyze` already uses for upstream-call failures per `src/ai/claude_cli.rs`). Exit code is 70 (EX_SOFTWARE). No new OtError variant is introduced by this story. |
