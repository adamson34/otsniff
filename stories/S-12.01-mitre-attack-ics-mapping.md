# S-12.01: MITRE ATT&CK for ICS technique mapping

## Narrative

- **As a** blue-teamer pasting an otsniff finding into an IR ticket
- **I want** each finding to carry its MITRE ATT&CK for ICS technique IDs
  (e.g. `T0859 — Valid Accounts`) with links back to attack.mitre.org
- **So that** otsniff's framing ("engineering-class CIP write") lands in the
  taxonomy my playbooks already use, without me hand-mapping it

## Context — what already exists

MITRE technique mapping is **partially present**: `RuleMetadata.references`
(`src/findings/mod.rs`) already supports `ReferenceKind::MitreIcsAttack` with a
display-ready `label` (`"T0859 — Valid Accounts"`) + `url`, and **8 of 15
detectors** already tag a technique (enip/s7/modbus/dnp3 engineering,
internet_egress, ntlmv1, rdp_legacy, recon_scan, unexpected_protocols). Two gaps
remain:

1. **7 detectors have no MITRE mapping** (`dns_resolver`, `ldap_creds`,
   `ntp_external`, `plaintext_creds`, `smbv1`, `stale_tls`, `weak_tls_cipher`).
2. The per-finding **analyze report (HTML/MD/JSON) does not surface** the
   techniques — only `otsniff rules` / `docs/RULES.md` do. The report enriches
   each finding with its catalog `trigger` (via `metadata_for(f.id)`) but not its
   MITRE references.

## Architecture decision (ADR-0014)

MITRE technique data stays in the **rule catalog** (`RuleMetadata.references`,
`MitreIcsAttack` kind) — the documented single source of truth that "can't
drift" (it lives next to the detector). P1-6 surfaces it per-finding by **looking
it up from the catalog via `finding.id`** — the exact mechanism the existing
`trigger` enrichment uses — rather than duplicating a `technique_ids` field onto
`Finding` (which would invite drift between the runtime finding and the catalog).
This deviates from the ROADMAP's literal "every Finding gains a `technique_ids`
field" for a sound reason; **the implementer adds `docs/adr/0014-mitre-mapping-in-catalog.md`**
recording this. Asserting-vs-supporting is expressed in the reference `label`
(a `"(supporting)"` suffix), avoiding a schema change.

## Acceptance Criteria

### AC-001 — Complete MITRE coverage for the 7 unmapped rules (traces to BC-3.06.006)

Each of the following detector modules adds a `ReferenceKind::MitreIcsAttack`
entry to its `RuleMetadata.references`, with `url`
`https://attack.mitre.org/techniques/T0XXX/`:

| Rule module | Technique | Label | Relationship |
|---|---|---|---|
| `plaintext_creds.rs` | T0859 | `T0859 — Valid Accounts` | asserts |
| `ldap_creds.rs` | T0859 | `T0859 — Valid Accounts` | asserts |
| `smbv1.rs` | T0866 | `T0866 — Exploitation of Remote Services (supporting)` | supports |
| `stale_tls.rs` | T0830 | `T0830 — Adversary-in-the-Middle (supporting)` | supports |
| `weak_tls_cipher.rs` | T0830 | `T0830 — Adversary-in-the-Middle (supporting)` | supports |
| `dns_resolver.rs` | T0884 | `T0884 — Connection Proxy (supporting)` | supports |
| `ntp_external.rs` | T0884 | `T0884 — Connection Proxy (supporting)` | supports |

- **Verification of correctness:** each technique ID MUST resolve to a real
  ATT&CK-for-ICS technique. The implementer confirms each of T0859 / T0866 /
  T0830 / T0884 against `https://attack.mitre.org/techniques/T0XXX/` (these are
  established ICS techniques; the existing 8 rules use the same `T08xx` space).
- **Test:** a catalog test asserting **every** rule in `catalog()` has at least
  one `MitreIcsAttack` reference (so future rules can't silently ship unmapped),
  and that every MITRE reference's `url` is `Some` and matches
  `https://attack.mitre.org/techniques/T0\d+/`.

### AC-002 — Per-finding MITRE surfacing in HTML (traces to BC-8.05.001)

`src/report.rs`: `FindingView` gains `mitre: Vec<MitreLinkView>` where
`MitreLinkView { label: String, url: String }`, populated from
`metadata_for(f.id)` by filtering `references` to `kind == MitreIcsAttack`
(empty when the id isn't in the catalog — same guard as `trigger`).
`templates/report.html`: render the techniques in each finding card as a
labeled line, e.g. a "MITRE ATT&CK for ICS:" row with each technique as an
anchor `<a href="{url}">{label}</a>` (target the MITRE site). Rendered only when
non-empty.

- **Test:** the HTML snapshot for a fixture finding shows its technique label as
  a link to `attack.mitre.org/techniques/T0XXX/`.

### AC-003 — Per-finding MITRE surfacing in markdown (traces to BC-8.05.001)

`src/report_md.rs`: after the existing `**Detection criteria.**` line (which
already uses `metadata_for(f.id)`), add a `**MITRE ATT&CK for ICS.**` line
listing each technique as a markdown link `[{label}]({url})`, comma-separated.
Rendered only when the finding's catalog metadata has ≥1 MITRE reference.

- **Test:** the markdown snapshot shows the `**MITRE ATT&CK for ICS.**` line with
  the technique link(s).

### AC-004 — Per-finding MITRE in JSON (traces to BC-8.05.001)

`src/cli.rs`: the `--json` findings payload (currently `"findings": findings`)
is enriched so each finding object carries
`"mitre_techniques": [{"label": ..., "url": ...}]` looked up from the catalog by
`finding.id`. Build the enriched array (map each `Finding` to a JSON object
plus the techniques); the rest of the finding fields are unchanged. (Both
`--json` write sites in `run_analyze` get the same treatment.)

- **Test:** the findings-JSON snapshot includes `mitre_techniques` per finding;
  a finding whose rule has no MITRE ref (none after AC-001 — all rules mapped)
  would serialize an empty array.

### AC-005 — `docs/RULES.md` regenerated

Adding MITRE references to the 7 rules changes `catalog()`, so the catalog
markdown (and thus `docs/RULES.md`) changes. Regenerate via
`cargo run -- rules > docs/RULES.md`; the `rule_catalog_matches_committed_rules_md`
test must pass against the regenerated file.

### AC-006 — Existing MITRE rules unaffected; no regression

The 8 detectors that already tag MITRE keep their existing references and render
identically through the new surfacing path (their findings now show the same
technique they already declared). Existing finding snapshots change **only** to
add the MITRE line/links; no finding's id, severity, evidence, or playbook
changes.

## Scrub Stance

### 1 / 2. What does this extract / render?

Nothing from packet content. MITRE technique IDs/labels/URLs are **static
catalog data** keyed by rule id — constant strings, no observed values. They are
rendered per finding in HTML/MD/JSON.

### 3. BCSI / scrub stance

**None.** Technique IDs/labels/URLs carry no asset identifiers; they are inert
with respect to the scrub layer and leak detector. The AI-bound markdown gains
constant MITRE strings only — the existing
`invariant_no_real_values_reach_ai_provider` continues to hold.

## Architecture Compliance Rules

- **Single source of truth:** MITRE data lives ONLY in the catalog
  (`RuleMetadata.references`). Renderers look it up by `finding.id`; do NOT add a
  duplicated field to `Finding` (ADR-0014).
- **ADR-0003:** HTML MITRE links use a pre-formatted `Vec<MitreLinkView>` on the
  view struct; template only iterates + anchors.
- **No new dependency.** Static `&'static str` data + existing `Reference`.
- **Determinism:** technique order follows the rule's `references` array order.
- **Output stability:** the only intended snapshot changes are finding
  HTML/MD + findings-JSON (the new MITRE line/array) and `docs/RULES.md`. Asset
  inventory / comms-matrix / capture-summary snapshots must not change.
