# S-2.04: DNP3 parser + engineering classification + `ics.dnp3_engineering` finding

## Narrative

- **As an** OT defender at an electric utility or water plant
- **I want** otsniff to recognize DNP3 traffic on tcp/udp 20000 and
  flag engineering-class function codes the same way it flags Modbus
  writes today
- **So that** the tool produces useful output on utilities captures
  where DNP3 is the dominant protocol

## Acceptance Criteria

### AC-001 (BC-1.02.005 — DNP3 PDU recognition)
- New module `src/parse/dnp3.rs` exposes `parse(payload: &[u8]) -> Option<Dnp3Event>`.
- Recognizes DNP3 frame: 0x05 0x64 sync bytes, length, control, dst, src,
  CRC; transport layer header (FIN/FIR/seq); application layer
  (control, function code).
- Function-code-level recognition only (no Object/Variation decoding).
- **Test:** Round-trip test with raw byte fixture for at least 5
  function codes including Operate (4), Direct Operate (5), Cold Restart (13).

### AC-002 (BC-1.02.005 — engineering classification)
- `is_engineering_dnp3(fc: u8) -> bool` returns true for: Operate (4),
  Direct Operate (5), Direct Operate No Ack (6), Cold Restart (13),
  Warm Restart (14), Initialize Data (15), Initialize Application (16),
  Save Configuration (24), Disable Unsolicited (20), Enable Unsolicited (21).
- **Test:** Unit test asserts each fc above is engineering; reads (1, 2, 22, 23) are not.

### AC-003 (observation pipeline integration)
- `Observer::ingest_packet` recognizes DNP3 on tcp/20000 and udp/20000
  and appends a `Dnp3Event` to `observations.dnp3_events`.
- `classify_flow` learns a `dnp3` label.
- **Test:** Synthetic PCAP fixture with DNP3 traffic produces
  `observations.dnp3_events.len() > 0` and `flow.label == Some("dnp3")`.

### AC-004 (BC-3.03.005 — `ics.dnp3_engineering` finding)
- New detector `src/findings/dnp3_engineering.rs` emits
  `ics.dnp3_engineering` at severity High (Critical if source is outside `--ot-subnet`).
- Evidence rolls up by `(src, dst)` pair with the fired function codes listed.
- `RuleMetadata` entry exists for `ics.dnp3_engineering` in `src/rule_catalog.rs`.
- **Test:** Snapshot test in `tests/snapshot.rs` with a deterministic
  `Observations` fixture containing 3 DNP3 engineering events from one host.

### AC-005 (RULES.md regenerates)
- `docs/RULES.md` includes the new rule.
- The `rule_catalog_matches_committed_rules_md` snapshot test stays green.

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-001 | Truncated DNP3 frame | Parser returns None; no panic |
| EC-002 | Bad DNP3 CRC | Parser returns None (treat as not-DNP3) |
| EC-003 | DNP3 over a non-20000 port | Not recognized (parser is port-gated) |
| EC-004 | Fragmented DNP3 (transport-layer FIN/FIR=0) | Out of scope for this story. Parser MUST NOT panic; instead return None on multi-segment frames. A follow-up roadmap entry tracks full reassembly; the story does not silently "document" a behavioral gap. |
| EC-005 | Capture has zero DNP3 packets | Detector emits no finding (existing pattern) |
