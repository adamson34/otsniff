# S-4.04: Kani composed proof of the privacy invariant

## Narrative

- **As a** compliance reviewer reading the README's "privacy
  invariant enforced by code" claim
- **I want** a composed Kani proof: `scrub` followed by leak_detector
  check, where the input contains real IPs/MACs/hostnames, terminates
  in either (a) all real values removed and Ok, or (b) Err
- **So that** the load-bearing privacy claim has formal evidence

## Acceptance Criteria

### AC-001 (BC-5.02.003 proven)
- `kani-proofs/composed_privacy_invariant.rs` proves: for any input
  string `s` (bounded length N) and any deterministic pseudonym map
  derived from values in `s`, the post-scrub bytes either pass the
  leak detector OR the leak detector returns Err. There is no third
  case where bytes pass but contain a real value.
- **Test:** `cargo kani --harness composed_privacy_invariant` proves.

### AC-002 (reviewer-ready summary)
- `docs/proofs/privacy-invariant.md` summarizes:
  - The three component proofs (S-4.01, S-4.02, S-4.03)
  - How they compose
  - What bounds remain (and why the unbounded claim follows)
